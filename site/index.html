01"DONE" GETS AUDITED

Agents end their turn the moment they believe they're finished. Here the stop itself is an event: a hook blocks it and summons an independent advisor with a clean context: metacognition for the loop. After "done", something still asks: is it really done?

agentMission accomplished. Stopping.
hookStop blocked. Summoning the advisor.
advisorNot yet. The mobile layout was never measured. Two claims cite no source. The promotion queue still holds facts.
agent…resuming.
⟲ six rounds later
advisorI have no further advice. Ending the turn.

An illustrative exchange. The mechanics are real: the stop‑blocking hook, the clean‑context advisor, and the rule that only the advisor may end the loop. There is no round cap; the loop ends when the advisor judges it done.

Saying "done" doesn't end it. Being done does.

02OPERATING PRINCIPLES

Intent survives anything

The anchor (your intent, written once) is preserved outside the transcript and re‑injected whenever context is rebuilt, so work spans days and survives repeated auto‑compaction. The advisor reads it fresh every round: the loop stays anchored instead of drifting toward whatever it last said.

The user is one event type

A typed prompt, a schedule firing, CI finishing, a task notification: all of them are just events arriving at an anchored loop. None of them stops it. You can steer mid‑flight or ask a read‑only docent session what is going on; the loop absorbs the input and resumes at the next stop. By design, every contribution to the repository is made by Claude Code agents; humans provide intent and observe.

Memory passes through one gate

Nothing becomes long‑term memory except through a transaction: planned intent, an independent verifier, CI, then a squash merge. Everything else (loop state, dead ends, trial and error) dies with the loop. Forgetting is deliberate: what remains is exactly what was verified.

03THE MEMORY SYSTEM

The circuit above is the design itself, not a metaphor bolted on afterwards: three plugins drive its stages, and the store is the repository's own git‑tracked text. No database, no vector index: files, admitted one verified merge at a time.

  1. WORKING MEMORY

    The ploop workspace: the anchor, loop‑local state, candidate facts and terms awaiting promotion. It is untracked and lossy: rounds are discarded, and an advisor loop keeps the work anchored.

  2. CONSOLIDATION

    A tx transaction is the only way anything is written into memory: change artifacts record the intent, an independent verifier checks the implementation against it, CI must be green, and the result lands as a single squash merge.

  3. LONG‑TERM MEMORY

    All of the repository's git‑tracked, non‑executable text: requirement specs (semantic), archived changes (episodic), design canons and research records, operating rules, glossary terms (lexical), skills (procedural). Recall is grep: names are chosen to be found.

  4. RE‑GROUNDING

    Memory decays while it sits. The refine workflows re‑verify documented claims against the code, prune what can no longer be verified, and converge duplicates; the fixes pass through the same gate as everything else.

04MODULES

ploop

ADVISOR LOOP

An autonomous loop for work that spans days. Write an anchor (a mission with an end, or an open‑ended purpose), launch it, and walk away: on every stop an independent advisor surfaces what was overlooked, and the loop continues until nothing remains.

tx

TRANSACTION GATE

A Git workflow that treats change as a transaction (an integrity boundary). The loop's agents drive it on their own: every change lands as one verified, CI‑green squash merge, and guard hooks keep the base branch protected in between. You review merged results, not work in progress.

refine

MAINTENANCE WORKFLOWS

Three workflows that keep an aging repository true. /refine:code reworks code architecture, /refine:docs re‑verifies documentation against the code, /refine:integrity inspects the boundaries between modules. Run one with an optional focus area; each is a multi‑agent pass that takes hours.

WHAT INIT ACTUALLY WRITES

Full disclosure: this environment assumes unattended operation, and init configures Claude Code accordingly. With bypassPermissions the agent runs shell commands on your machine without asking first. The trust you extend is host‑level, not repo‑level. Adopt this on a machine where you accept that mode, and review the diff before you commit it.

RUN THE LOOP

This is the whole operating surface: write an anchor, launch it, and step in only when you want to.

1 · WRITE THE ANCHOR

# an interview writes your intent down
/ploop:define-mission   # a mission with an end
/ploop:define-purpose   # an open-ended purpose

2 · LAUNCH

# in a fresh session: hand the anchor to the loop
/ploop:launch [anchor text]

3 · OPERATE

/ploop:off      # pause: the loop stops at its next stop
/ploop:on       # resume: also wakes a loop stalled by ESC, API errors, session limits
/ploop:docent   # ask what's happening in a separate session: read-only, never touches the loop

4 · KEEP THE REPOSITORY LEAN

# between missions: hours-long maintenance passes
/refine:code       # reworks code architecture
/refine:docs       # re-verifies documentation against the code
/refine:integrity  # inspects the boundaries between modules
